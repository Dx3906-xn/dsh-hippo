# dsh-hippo

长期记忆插件，为 [DSH](https://github.com/deepseek-ai/deepseek-harness) 的陪伴型智能体设计。

一句话：**关系状态是产品，记忆库是基础设施。**

大多数「agent memory」把记忆当成检索问题——写进去、搜出来、塞回 prompt。这对客服机器人够用，对长期陪伴的人不够。一个人记住你，不只是记得你说过什么，还包括：什么时候开始记不清了、哪些是随口一说、哪些是真的要紧、你现在和上次说的不一样了、以及他更信任你了还是更小心了。

hippo 试图把这些都变成可计算的机制。

## 为什么不用现成的

DSH 生态里有十几个记忆插件。评估过的都缺同一组东西：

| 缺失 | 后果 |
| --- | --- |
| 没有遗忘 | 一年后的 prompt 里塞着第一天随口说的废话 |
| 没有巩固 | 原始对话堆着，没有从「他说过」变成「我知道」 |
| 没有情绪权重 | 「我妈住院了」和「今天天气不错」权重一样 |
| 没有矛盾演化 | 搬家之后旧地址还在，两个都"正确" |
| 没有关系状态 | 聊了三个月和第一天，说话方式一模一样 |
| 中文检索坏 | FTS5 的 `unicode61` 把整句中文当一个 token |

最后一条是实测的，不是推测：

```
unicode61 分词下 MATCH '加班' → []        # 整句中文被当成一个 token
bigram 预分词后 MATCH '加班' → 命中
```

所以 hippo 自己做分词（`lib/tokenize.js`），中文用重叠 bigram，索引串和查询串都过同一套。

## 它怎么工作

四层记忆，越往上越慢、越贵、越像"知道"：

```
L0 感觉   原始消息                        不直接读，只在需要时回查
L1 工作   当前上下文                      由 DSH 的 compaction 管，hippo 不碰
L2 情景   episodes  —— 谁在何时说了什么     不可变，只标记被谁吸收
L3 语义   facts     —— 提炼出的稳定认知     可修正，有版本链
L4 程序   relationship / open_loops       关系状态与未完成的事
```

### 写入：三级闸门

不是每句话都值得花 token 提炼。

1. **闸门一（零成本，每轮）**：原始消息直接落 `episodes`。规则词表判断是否值得往上走（`lib/gate.js`），命中显式记忆、自我披露、关系事件、承诺、更正、情绪中的任一类才开门。
2. **闸门二（攒批）**：未处理内容累计到 4 条、或超过 2000 token，才发一次抽取调用。一次调用看整批，硬 JSON 契约（`lib/extract.js`）。
3. **闸门三（审计）**：抽取结果再过一次廉价审计，拦掉"模型自己脑补"的条目。审计调用失败时**降权保留而不是丢弃**——丢掉一条真记忆比带一条软记忆糟。

### 决策：ADD / UPDATE / INVALIDATE / NOOP

mem0 的形状，两处不同：

- **矛盾只退休不删除。** 旧事实保留 `invalid_at` 和 `superseded_by`，belief 的历史可查。这是"改变主意"和"从来不记得自己想过别的"的区别。
- **单值性是谓词的性质，不是句子的性质。** `lives_in` 换了城市就是矛盾；`likes` 加了新爱好是并列。这套判断写在 `SINGLE_VALUED` 集合里，不交给模型每次现猜。

谓词走白名单归一（`PREDICATE_SYNONYMS`）。模型会顺手写成"养了"或"是"，而键一漂移，两条陈述就永远无法比较。

**第四个动作：子集不算新事实。** 判断矛盾靠的是两条陈述的字面相似度，而这个度量会被长度差稀释——真实库里撞到的一次是 `objectSimilarity('上个月查出糖尿病，目前在控糖；血糖这周稳定了，她松了一口气', '血糖') = 0.077`，远低于进入 UPDATE 带的阈值，于是"血糖"作为一条新事实插了进去，此后 `妈妈 health` 在常驻段里并列陈述两遍。所以长度比较被单独提出来：候选的 object 是被已存值**包含**的（信息更少），判 NOOP；反过来包含已存值（信息更多，比如"咖啡"→"美式咖啡"），才走 UPDATE 带。方向反了就会用碎片覆盖完整记录。

**第五个动作：改述也算同一条。** 字面 Dice 对长度差敏感的方向正好错：「猫绘本稿已于今天交稿，出版社下周给反馈」和「绘本稿已交，出版社下周给反馈」是 0.69，换到「等出版社下周给稿子的反馈」只剩 0.43 —— 跨在 UPDATE 门槛两侧，同一件事于是被存了两遍。不同的事则几乎不共享内容词（实测最高 0.17）。所以 UPDATE 带加了第二条通路：**内容词重叠 ≥3 个且包含率 ≥0.5**。包含率用 `min(|A|,|B|)` 做分母，因为同一件事的两种说法详略可以差很多，但共同的那部分一定被两边都覆盖。一两个共享词不算——「一直想养只猫」和「想养猫，但现在租的房子房东不让养」只共享「养猫」，合并会丢掉真正要紧的那句限定。

**第六个动作：完成覆盖它完成的那一条。** `plan` 和 `habit` 也是多值的——一个人手上同时有复查、婚礼、见客户、换工作好几件事，把它们当单值会让常驻段只显示六件里的一件。但多值有个明显的代价：完成了的计划不再覆盖任何东西，库里就同时躺着「下周要交一本猫的绘本稿」和「猫绘本稿已于今天交稿」，两条现在时并列。所以多值分支里加了一条收窄的规则：**候选带完成标记，且与某条更早的同谓词事实共享 ≥2 个内容词，就退休那一条**。「还没交，下周继续赶」不算完成（否定前缀先判），「下下周一去参加婚礼」不会覆盖稿子（不共享内容词）。方向是单向的：完成覆盖未完成，反之不成立，否则每次重述计划都会把上一条打掉。

### 读取：三段

1. **常驻段**（system prompt，`lib/prompt.js`）：一行时钟 + 关系状态 + 核心事实 + 对方身边的人 + 还没聊完的事 + 最近聊过的。预算 1200 token，压缩到 75% 就截断。渲染时 `interpolate: false`，不参与 DSH 的 `{{}}` 模板替换。
2. **召回段**（按需）：命中"你还记得吗"这类提问时，检索并按需注入。标记为 `form: 'recall'`，下一轮不会被当成新消息再记一遍。
3. **显式工具**：`memory_recall` / `memory_state` 等，给模型自己查。

**问题本身也可能是空话。** 「你还记得我什么样吗」的分词结果是 `还记 / 记得 / 得我 / 么样 / 样吗`，全是问句脚手架，一条也命中不了——没有种子，图扩散也就无从展开，整段召回空着回来。而这恰恰是最不能空着回来的时刻：对方正在问「你到底记住我什么了」。所以自动召回在词面全空时退回按显著性取行（固定事实、高置信度、高唤醒度，各按权重排序），给一个下限而不是答案。`memory_recall` 工具不走这条退路——工具是精确查询，用一个不存在的词去搜却拿到主人最难忘的几件事，只会让模型以为自己的查询被听懂了。

**时钟。** 常驻段第一行是「现在是 2026-10-18 凌晨」。DSH 有官方的 `dsh-time-context` 包，但 companion preset 不挂它（它占一份 prompt 预算，而这里已经有常驻段了），没有这一行模型不知道今天是几号——「明天就要交稿了」存进去三个月后仍然写着「明天」。

**注入的消息必须带着身份进日志。** 召回段和 agenda 段是插件自己造出来的 user 消息，追加进这一轮的 batch 后会被会话日志原样落盘。DSH 的会话日志要校验它存下的每一条消息，缺 `id` 就拒收——而它拒的是**整个会话**：下一次 `--session-id` 续接时整段历史都读不出来，报 `stored session "..." is corrupt: event at seq N lacks an identified message`。手搓一个 `{role, content, source}` 对象字面量正好落进这个坑，而且发作得极其隐蔽：之前每轮召回块和 agenda 都是空的，什么都不注入，所以一直没事；等到记忆第一次真的有东西要说（那轮刚有一条待澄清），那一句才把会话写坏，再下一轮续接才炸。造消息一律走 `createUserMessage()`——它顺手把 id 和冻结一起做了。这条错误单测同样看不见，因为 `apply()` 的桩上下文不校验事件形状；`test/wiring.mjs` 现在会断言注入 batch 里每条消息都有 id。

激活分数是五个因子的乘积：

```
score = (0.5·activation + 1.0·relevance + 0.4·salience + 0.3·recency) · r · fan
  activation  ACT-R 基级激活 ln(Σ t_k^-0.5)
  relevance   BM25 归一
  salience    0.6·置信度 + 0.3·敏感度 + 0.4·情绪唤醒
  recency     指数衰减
  r           FSRS 可提取度
  fan         联想扇效应，撞太多条就降权
```

**salience 里的第三项是重点。** 只按敏感度和置信度算，「我妈住院了」和「今天天气不错」存进去之后权重一样——它们是同一批抽取出来的，置信度相同，都不是私密话题。唤醒度是消息自己的属性，所以它在写入时就落在 `episodes.arousal` 上（schema 6），不是事后从 `affect` 时间线里反推。

**主题扩展。** 人按话题提问，库按属性存。问「我工作怎么样」和存着的 `works_as=插画师` 一个字都不重，纯词面检索返回空。`lib/topics.js` 是一张话题→属性键的映射表（工作→`works_as`/`works_at`、猫→`has_pet`、讨厌→`dislikes`……），命中时把属性名并进 facts 的 MATCH 表达式。episode 不参与扩展——对话日志要搜的是「原话」，加进去会把每句带「职业」的话都捞出来。这张表故意写死的：可读、零成本、改错一行就够，不需要重训。同义词（插画/画画/画师、猫/喵）只在**写入时**进索引体，不在查询时展开：索引建一次查每轮，而查询侧展开会撞穿 FTS5 的 14 个外层谓词上限。

**回忆要能被评价，否则稳定性永远不变。** 检索本身只说明「这条和查询匹配」，说明不了「这条对不对」。所以每次注入召回块时，被真正渲染出来的行会记成一份待评分快照（`pending_recall`），等对方下一句话到齐再结算：话里复述了这条（取前 24 字做子串判定）→ grade 4，稳定性上涨；话里纠正了它（「不对」「你记错了」「其实不是」）→ grade 1，稳定性下跌。没有这一步，所有事实的 `stability` 会停在提取时给的初值，FSRS 遗忘曲线退化成一条纯时间衰减的直线，复习次数永远为零。

这份快照存在库里而不是进程内存里，因为最常见的调用形态是每轮一个新的一次性进程——进程内 Map 连下一句话都活不到。代价是它必须**读一次就消费掉**，否则下一次无关回复会替上一轮的记忆打分；以及必须有 30 分钟窗口，因为进程退出时没有定时器会清理过期行。

### 关联图

`links` 表存三种边，在巩固时构建：

| 边 | 语义 | 权重 |
| --- | --- | --- |
| `temporal` | 同批相邻的两条 episode | 0.4 |
| `supports` | 事实 → 说出它的那句话 | 0.7 |
| `semantic` | 两条事实的词袋有交集 | 0.2 + 0.1·交集 |

**故意不写 `shared_subject`。** 同一个人身上的所有事实共享同一个主语，按主语连边会得到一张完全图——里面没有任何东西离任何东西更近，扩散退化成按插入顺序遍历。实测跑出来 72 条边，等于没有连接。真正的关联来自共享词汇和「当时是一起说的」。

扩散（`spreadActivation`）区分**加权**和**准入**：词面命中的行，邻居只帮它加分；没被命中的邻居，只有在词面命中太少（少于 `max(2, limit/2)`）时才准入。具体的 cue（「橘猫」）已经知道自己要什么；模糊的 cue（「你记得我爱做什么吗」）才需要图来找路。

### 来源

每条事实都能追回说出它的那句话。`memory_remember` 走的是显式路径，中途从会话里取最近一条用户 episode 作为锚点——不这么做，显式写下的事实就是一堆没有出处的断言。巩固路径走抽取时自带的 episode 索引，并且更新旧事实时会连同已存的 evidence 一起重连，所以「三周前说过、今天只是重申」的事实仍然连着三周前那句原话。

### 谁是谁

一个库里有两种主语，而且都会坏：

- **主人自己**。抽取器按 `subject: "user"` 写，但句子说「我叫林晚」时它有时会把下一条事实记在「林晚」名下。那些行存住了、索引了、连边了，然后所有按 owner 过滤的读路径都看不见它们。`applyFacts` 现在从 `name`/`nickname` 事实里取别名，在写入时把主语归一；schema 8 迁移修历史行。
- **别人**。「妈妈 health = 糖尿病」这类事实以前根本没进过 prompt——常驻段只查 `subject = owner`。可陪伴场景里最该记住的往往正是这些：朋友的母亲得了什么病，比他本人血型重要得多。现在有一段独立的「对方身边的人」，健康、关系冲突类加权，最多 5 条。

这两类 bug 有一个共同点：**数据看起来完全健康**。`memory_state` 的计数正常，常驻段照常渲染，只有在真的问起那件事、或者翻索引时才发现它是空的。所以测试里有一条不变量——每条 live fact 都必须有对应的 FTS 行。

索引是派生数据，于是修复原则只有一条：**扔掉重建，别打补丁**。schema 7 / 8 / 9 三次迁移都栽在这里：7 修一次写入路径的损坏，8 在重建索引时用了自己 UPDATE 之前的快照（被改名的行反而从索引里消失），9 才改成无条件全量重建。少一条索引比多一条坏索引更难发现。

### 遗忘：两件不同的事


**衰减**是系统判断「这条不重要」。`lib/fsrs.js` 是 FSRS-5 的简化实现，19 个权重 + 可提取度公式 `R(t) = (1 + FACTOR·t/S)^DECAY`。检索得越好，稳定性越涨、下次越难忘；21 天没被碰过、置信度低、可提取度掉下来的事实，`demoteWeakFacts` 每轮微降一点置信度，掉到 0.18 以下就退休（保留行和版本链）。**高可提取度本身就是它重要的证据**，所以 R ≥ 0.55 的一律不动。姓名、昵称、生日这类谓词进 `PINNED_PREDICATES`，永不衰减——忘掉一个人住哪个城市是合理的，忘掉名字是 bug。

**遗忘**是人要求「别记这个」，必须立即、彻底、不经过模型判断。`asksToForget` 命中后直接 `redactRecent`：清空 `episodes.text`、删 FTS 行、删 evidence 行、只由被删的那句话支撑的事实一并退休。走模型自主决定意味着「记忆系统必须永远服从的那一条指令」恰好是它可以拒绝的那一条。

**摘要也是那句话的一份副本。** reflection 是用它覆盖的那几条消息写出来的，所以被忘掉的原话**逐字**躺在摘要正文里，而摘要「最近聊过的」每轮都进常驻段。没有句子级的溯源可以精确剪掉它，所以引用了被删 episode 的摘要整条作废、正文清空，它覆盖过的其余消息退回未巩固队列（被删的那条除外），下一轮不带它重新成摘要。**只删 episode 不删摘要，等于把那句话换个地方留在提示词里。**

这两件事曾经共用 `episodes.superseded_by` 一列，后果是**每个被巩固过的 episode 都看起来已被遗忘**，而真正的遗忘请求在那些行上是 no-op。schema 4 把 `redacted_at` / `redacted_reason` 拆了出来——巩固标记和遗忘标记不是同一种事，别让它们抢一个格子。

### 关系状态

不是记忆的一部分，但决定记忆怎么被使用。四件事：

- **熟悉度**由活跃天数和对话量推出，`1 - exp(-(activeDays/12 + episodes/400))`。
- **信任**只由「关于关系本身的语句」驱动：自我披露、修复、划边界。**绝不由消息量推断**——那是陪伴型 agent 变成应声虫的起点。降得比升得快，恢复的速度等于建立的速度就说明它什么都没在追踪。
- **情绪基线**是 affect 观测的滑动均值。
- **还没聊完的事**是 open loops，到期会进常驻段。

全部渲染成**散文**，不是百分比。「熟悉度 37%」模型要么忽略，要么照念；「你们已经聊过一阵子，对方还在观察你；最近这段时间对方的状态偏低」它能据此行动。

### 巩固

三个触发点：闲了 15 分钟、agent 退场、或者未巩固内容攒够 50 条。做四件事：

1. **抽象**：把一批 episode 压成一条 reflection。摘要用本批抽出来的事实做主题（「12 条消息，聊到：苏州、晚晚」），抽不出主题时退化为最长的一句原话。**「12 条消息，起于：……」不是摘要，那是行数加一句引文。**
2. **抽取**：模型从原文里抽事实，再过一遍审计。
3. **应用**：每个候选过 `decide()`，ADD / UPDATE / INVALIDATE / NOOP。
4. **链接**：建上面那张关联图。

关系状态**不**等巩固——它依赖每轮都会到的观测，挂到巩固上意味着 `mood_baseline` 要等攒够一批才更新，实测停在 0 停了好几个小时。

⚠ 一次性会话（headless）在 turn 结束时就会退出进程，所以 turn boundary 也触发巩固并等待最多 4 秒；退场时再等最多 15 秒让在途的巩固落地。否则整个批次的记忆会随进程一起消失——这个 bug 实测踩过。

### 待办：agenda

常驻段之外还有一段按需注入的「你手上还记着的事」，两百来字：

- **还没等到回音的事**：`detectLoop` 从原话里认六类——正在进行的事、有期限的事、对方身边发生的事、当下的情绪、悬着的事、还没定的事。情绪类 18 小时后就可以问，其余压 6 小时。**上限 8 条**，只取到期的前 3 条：永远满的 agenda 是一个模型学会忽略的 agenda。
- **还没解决的矛盾**：`needs_clarification` 的事实，最多 2 条，带上一句「你先后记下了 X 和 Y，还没确认哪个对」。

循环会被关闭——「我终于戒掉了」关掉戒烟，「我没戒掉」不关。判据是 `{phrase, topic}` 配对：phrase 测这一句，topic 测那一条 loop。**方向反了就全错**：拿「戒」字做共享子串，`稿子终于交了` 会把戒烟关掉（共用「了」），`我终于戒掉了` 反而关不掉（只共一个「戒」）。

配对本身还不够。有一类动词自带宾语——「戒掉了」和「我在戒烟」没有一个字相同，主语只能由那条 loop 提供；另一类挂在什么词后面都行——「好了」。放宽词表时漏了这一层，`婚礼的礼物买好了` 把「我下周三要去医院复查」关掉了：`买好了` 命中「好了」，`医院` 由 loop 提供，于是一个还没发生的预约看起来被一个婚礼礼物解决了。所以除 `selfSufficient` 的动词外，topic 还必须在**这一句里**也出现——这正是 loop 没法替它补上的那一半。四条真正该闭合的（交稿、复查、戒掉、回不回去）在收紧后依然各自关掉各自的环。

中英两套 pattern **同时生效**，不按 `language` 配置挑一套。配置里的语言是**提示词**的语言，不是对方打字的语言——一个人完全可以用英文界面写中文。按配置挑词表的话，两者一旦不一致，loop 就不再开启，而且没有任何报错：表一直在，写的人没了。两套词表也不会互相误伤，字母表是分开的。

两边的「自带宾语」判断并不一致，这是语言本身的差别：英文用代词顶替宾语而不是省略它，`handed it in` / `submitted` 单独出现就够具体，所以那一组是 `selfSufficient`；中文的「交了」「发了」不够——`我发了` 可能是消息、是钱、是快递。

矛盾问题两周没被回答就静默过期——这周值得问的问题，一个月后不值得再问。

agenda 和召回是**两条独立的路**。曾经写成「没有召回就直接返回」，结果问候轮永远看不到 agenda，因为「在吗」不触发召回。现在两段各自判断、各自注入，标成 `form: 'instructions'` 的那种会在下一轮被跳过，不会被当成真人发言再记一遍。

### 澄清

单值谓词（`lives_in`、`works_as`、`age`……）出现新值时，不直接覆盖，而是把新的标成 `needs_clarification`、旧的退休，等模型择机问一句。三种收场：`keep_new`（新值提信心）、`keep_old`（**复活**旧行，连同它的 evidence 和复习历史）、`both_wrong`（两边都退休——属性留空好过留猜测）。多值谓词（`likes`、`has_pet`）不会触发澄清：「喜欢咖啡」和「喜欢爬山」是共存，不是矛盾。

判定相似度用 bigram Dice 系数，阈值三档：≥0.85 视为同一条（NOOP）、≥0.45 视为同一条的详略版本（UPDATE）、否则才当冲突。包含关系（「插画师」vs「插画师，主要接商业稿件」）落在 UPDATE 带而不是冲突带——那是同一件事说得更全，不是改口。

### 时间：话里的日期必须当场解掉

`schema_version` 里其余所有时间都是绝对时刻，只有一件事不能这么办：人说的话。

「下周三要去复查」这句话成立期正好一周。一周后同样几个字指向另一个日期，或者不指向任何日期——所以一个只把字存下来、以后再读的库，存的是会悄悄变成假话的东西。

解法不是把原话改写成日期，而是**解一次，和原话并列存**。原话保持可引用，解出来的时刻保持正确：

- `parseRelativeDate(text, now)` 中英两套词表，和 loop 的检测路径同一个原则：**两套同时生效，不按 `language` 挑**。认的写法：显式日历日（`10月21日` / `October 21` / `21 October`）、「明天/后天/大后天/昨天」与 `tomorrow` / `the day after tomorrow` / `yesterday`、星期（**「下周三」从周一是 9 天后，不是 2 天后**——`下` 和 `next` 都加 7 天，因为它们指的是**下一周的那一天**，不是下一个到达的那一天）、「下个月/月底/年底」与 `next week` / `this weekend` / `the end of the month` / `the end of the year`、「过几天」与 `in a few days` / `a fortnight` / `in two weeks`。
- 没说钟点就落到**当天 23:59**。没有钟点的日期意思是「那天某个时候」，而适合追问的时刻是它的末尾：周三零点问「复查怎么样」只会得到「还没去」。
- 钟点也分两种语言：`3pm` 和「下午三点」必须落到同一个时刻。只读中式的 `点`/`:` 会把下午的预约放进凌晨三点，而那是**看不出错**的一种错——时间是合法的，只是差十二小时。
- `due_at`（事什么时候发生）和 `follow_after`（什么时候适合提）**是两列**。合并它们就是那个让复查当天晚上就来问的 bug。
- 渲染时如果原话自己还带着日期（`namesItsOwnDay`），就不再补一句「指的是明天」——重复的括注会让模型学会跳过括注，包括那些真的带信息的。

三处**故意不解析**，都是「猜错比不猜更贵」：

- `10/21`：在美国是十月二十一日，在别处是十月……另一种十月二十一日。方向错的那一半会把追问放到一个从没被提起的日子上。
- `for two weeks`：这是「已经持续了多久」，和中文的「已经两周了」一样。当成日期解出来，追问就落在过去，只能立刻触发。`three days ago` 反过来是**可以**解的：那是过去的一个时刻，`followUpAfter` 会把它压到下限，于是「手术是三天前做的」当天就能问。
- 历史 loop 的 `due_at` 留空是有意的：从几周前的文字倒推日期会把预约放到错误的那一天。

## 中文检索

SQLite 的 FTS5 `unicode61` 分词器按空格和标点切，一整句中文会变成**一个** token：搜「加班」对「我最近老是加班」返回 0 行。所以这里自己预分词，索引串和查询串用同一套规则。

索引时**同时写 bigram 和 unigram**。只写 bigram 的话，单字查询（「猫」）永远匹配不到长串里的那个字——「橘猫」里没有独立的「猫」。unigram 只进索引、不进查询，所以不会把命中集撑大。代价是中文索引大约翻倍。schema 3 的迁移会重建两张 FTS 表。

## 工具

模型可见的只有八个，刻意压得少——陪伴型对话里模型几乎不会主动调记忆工具，给多了只是占 prompt：

| 工具 | 用途 |
| --- | --- |
| `memory_recall` | 精确检索。**不带模糊回退**：查不到就说查不到。打印每条结果的短 id。 |
| `memory_remember` | 写一条事实，走同一套决策（含主语归一）。 |
| `memory_forget` | 用 id 退休一条事实，或用 id 忘掉某句原话（连带引用它的摘要）。从不物理删除。 |
| `memory_open_loops` | 列出还没等到回音的事，每条带短 id。 |
| `memory_loop` | 手动开/关一个 loop。关闭要的是 `memory_open_loops` 打印的 id。 |
| `memory_state` | 计数、待澄清清单（带 id）、以及模型眼中的常驻段。 |
| `memory_consolidate` | 手动触发一次巩固。 |
| `memory_clarify` | 用 `memory_state` 打印的 id 回答一条待澄清：`keep_new` / `keep_old` / `both_wrong`。 |

**id 必须由某个工具打出来，否则这个工具等于不存在。** 三个工具（`memory_forget`、`memory_loop` 关闭、`memory_clarify`）唯一的输入是一个 id，而它们只能拿到别的工具打印过的 id。原来 `memory_recall` 只打内容、`memory_state` 只打计数，于是这三个工具在真实对话里**从来无法被调用**：模型想删掉某条被点名的记忆，手里没有任何东西可以传，只能去磁盘上找数据库。单测里每个工具都自洽，所以这件事在 30 个套件全绿的情况下存在了很久。现在 id 打印成前 8 位（够唯一、省 context），所有查表都先精确匹配再唯一前缀匹配——前缀撞上两行就返回空，猜错一条记忆不是记忆系统该做的事。`test/wiring.mjs` 里加了一段「一个工具打印的 id 必须在消费它的工具里解得开」的往返测试，这才是能抓住这类错的形状。

**打印出来的 id 还得真的解得开——而这个问题只能在第二个主语存在时才暴露。** 第一版的 `memory_forget` 在自己的事实里找 id：`liveFacts(db, { subject: owner })`。读的路径从来不按主语过滤（`memory_recall`、`memory_state` 都会把「妈妈 / works_at」连 id 一起打印出来），只有这一个写的路径过滤了。于是真机上一件很具体的事发生了：模型想纠正一条被安错人的记录，先 `memory_recall` 拿到 `[0dff2dee]`，再 `memory_forget 0dff2dee`，得到「no such memory」——**一条刚刚被打印成 live 的事实，工具说它不存在**。`test/wiring.mjs` 的夹具此前每一条事实都属于主人，所以那段 id 往返测试是绿的：**只处理一个主语的测试看不见作用域问题，它需要第二个主语存在**。现在夹具里有一条 `妈妈 / works_at`，断言就是「他人事实的 id 也能被退休」。

e2e 里对应的那条断言一开始写错了，值得记下来：它数的是结果里出现几次「no such memory」，一次都不许有。跑出来有，但原因和缺陷无关——模型在**同一个 step 里**同时发了 `memory_remember`（改成苏州）和 `memory_forget`（退掉北京那条），remember 先把那一行退休了，forget 才轮到执行，于是工具**正确地**回了一句「只退得掉还活着的事实」。一次拒绝因此不是缺口，把拒绝数当指标才是。真正要证的是模型**没有猜 id**：现在从工具结果里收集所有 `[xxxxxxxx]`（只收结果，不收模型自己的话），再检查它传给工具的每个 id 都在这张表里——「ids passed to tools: 4; not printed by any tool: 0」。这才是「id 由工具生产、由工具消费」这条链的可证形式，而它不需要假设模型会按顺序行事。

## 成本

一条日常对话每天大约：抽取 2 次 × 6K in + 800 out，审计 1 次 × 3K in。约 **110K token/天**。用 `deepseek-flash` 级别的小模型跑，实际可以更低。

关掉 `extraction` 后是纯零成本：只落 episodes，不做提炼，召回仍然可用（走 FTS）。

`wiring.mjs` 是唯一能证明接缝对了的测试：事件名、工具 schema、注入位置错一个，前几个测试照样全绿。

`identity.mjs` 守的是一类特别安静的 bug：数据存住了、测试绿了、`memory_state` 数字正常，但那条记忆在检索里根本不存在。所以它断言的不变量是「每条 live fact 都有索引行」，而不是某个具体查询命中。

`scale.mjs` 的写法有一条约束：**只测耗时会骗自己**。一个返回 0 行的查询当然快，所以每一个延迟断言旁边都配一条行数断言——「模糊提问在 4.7ms 内返回 20 行」是结论，「模糊提问在 4.7ms 内」不是。

`profile.mjs` 验的是「快照不自我矛盾」：库里可以同时留着杭州、苏州、合肥三条 `lives_in`（那是版本历史的本分），但常驻段只能陈述一条，且必须是最新的那条。它同时钉住了多值谓词的上限，和「子集不新起一行」这条规则的方向。

`grading.mjs` 和 `pending.mjs` 是一对。前者证明「回忆被复述 → 稳定性上升、被纠正 → 稳定性下降」这条链路在代码里是通的；后者证明它跨得过进程边界。这两件事必须分开测，因为失败的样子完全不同：前者坏了是评分永远温和，后者坏了是评分永远不发生——而第二种在单进程里跑一切正常。

`migrate.mjs` 不是测试，是升级前的规矩：先 `Copy-Item` 一份库，让副本走完迁移并打印结果，确认「退役了哪几条、留下了哪几条」之后再动原库。它救过一次——迁移 14 在副本上被发现会把两件不同的计划判成同一件。

`agenda.mjs` 里那组英文用例盯的是一类**半边双语**的 bug：渲染路径是双语的（标题、日期、年龄、问法都有英文分支），检测路径却是纯中文的。这种不对称不会报错，也不会让任何一条已有断言变红——英文部署下 agenda 表永远是空的，而渲染器读得很正常。所以英文用例必须和中文用例并排放在同一个文件里，而不是塞进 `i18n.mjs` 的「英文路径没有半截中文」那类检查里：后者测的是文字，前者测的是**根本没有东西可渲染**。

单元测试证明不了「英文那一条真的走到了存储」，所以双语改动要在一份**独立的 DSH_HOME** 上再跑一遍真对话：复制一份 home，删掉 `hippo` 与 `sessions` 得到空库，profile 里的 `call` 指向本仓库。两个坑都踩过：

- `Copy-Item -Recurse` 会把 junction **展开成真副本**。于是那份插件是复制那一刻的快照，之后改的代码在副本里完全不生效——现象是「loop 没开」，看起来像检测逻辑的 bug，其实是跑的旧代码。复制之后要把 `profiles\call\node_modules\dsh-hippo` 换成指回仓库的 junction（`cmd /c mklink /J`），之后每次改动即时生效。
- 反过来，删这份 home 之前必须先 `cmd /c rmdir` 掉那个 junction：PowerShell 5.1 的 `Remove-Item -Recurse` 会顺着 junction 递归下去，删的是**仓库本体**。

跑法（第一轮开 loop、第二轮问「我刚才在担心什么」看它读不读得到、第三轮说完成）：

```powershell
$env:DSH_HOME='D:\A\DSH-L\agent\home-en'
$bin='D:\A\DSH-L\agent\node_modules\@deepseek-ai\dsh\lib\bin.js'
node $bin --profile call "I have to hand the illustrations in next Wednesday and I am badly behind on them"
node test\loops.mjs 'D:/A/DSH-L/agent/home-en/hippo/memory.db'
```

断言的是库里的行：`due=2026-10-21T15:59 (next Wednesday)`（周日说的「下周三」= 那天 23:59）和 `closed/resolution`。只看 agent 的回复会漏掉一半——它可能什么都没说。

`test/` 下的文件分三类：断言套件、观察脚本（`dbstate` / `live` / `loops` / `reflections` / `show-prompt` / `inspect-*` 等），以及 e2e——观察脚本只打印不打断言，e2e（`e2e-forget` / `e2e-tools`）要一个空的 DSH_HOME 参数并且真的烧 token，所以全量跑的时候两类都要排掉（排掉是手工的：它们缺参数会报 FAIL，那不是回归）。断言套件加上这两类，覆盖的是「机制自己转不转」，覆盖不了「机制转起来有没有用」。后者只能看真实对话——比如 agenda 写好了但 `open_loops` 表一直是空的，是 `detectLoop` 太窄还是没人触发；这种问题 grep 导出的调用点比读代码快得多：

```powershell
# 哪些导出函数零调用？（文档写了、测试绿了、但对运行的 agent 毫无影响）
foreach($f in Get-ChildItem lib\*.js){
  foreach($m in ((Get-Content $f.FullName -Encoding UTF8) | Select-String '^export (async )?function (\w+)')){
    $fn = $m.Matches[0].Groups[2].Value
    $n = (Select-String -Path lib\*.js,test\*.mjs -Pattern "\b$fn\b" -Encoding UTF8 | Measure-Object).Count
    if($n -le 1){ Write-Host ("UNUSED {0,-24} {1}" -f $fn, $f.Name) } } }
```

这张清单曾经一次列过九个 —— `demoteWeakFacts`、`liveReflections`、`asksToForget`、`fadingFacts` 全在上面。测试全绿，功能全死。

同一个形状换个粒度就是 `tableaudit.mjs`：**哪张表只写不读**。`reflection_evidence` 长期列在上面——巩固时写进去、迁移时回填过，运行时从来没有一条语句读它。一张没人读的表不是备份，是一个没人来的房间：它的存在让「摘要知道自己是哪几句写出来的」看起来已经实现了，而实际上没有任何行为依赖它，所以「忘掉那句原话」也就到不了覆盖它的摘要。**写入方和读取方如果是两个人写的，中间那根线没人验。**

还有一类错在**观察工具自己身上**，它比被测的代码更容易骗人，因为它一骗就骗在「看起来像被测代码坏了」的方向。`test/session-log.mjs` 就是为这个存在的：DSH 的会话日志是按 flush 写成**很多个 zstd 帧**的（一次四轮的对话 57 帧），而 Node 暴露的每个解压 API 都**只解第一帧**——`zstdDecompressSync()` 和 `createZstdDecompress()` 都只返回 188 字符的会话头，不报错、不提示截断。于是 e2e 里「模型到底调没调这个工具」的字符串搜索对每个工具都返回 false，而库里明明有那些工具写下的行；看起来完全是工具链断了。现在按帧魔数切开逐帧解，并且 e2e 在读完之后先断言「这份 transcript 至少 1000 字符」——**观察者的输出要先自证，再拿去当证据**。同一个文件另外导出 `toolCallsOf()` 与 `printedIdsOf()`，把「模型到底把什么传给了工具」和「工具到底打印过哪些 id」变成两个集合，于是可以断言前者是后者的子集；按字符串数错误出现几次是做不到这件事的，因为它统计的是模型的随机行为，不是系统的契约。

## 不做的事

- **不碰 L1 工作记忆**。上下文窗口和压缩是 DSH 的事，hippo 只在 `agent/pre-step` 上挂一条。
- **不做向量检索**。中文 bigram + BM25 + 话题扩展在这个规模上够用，加 embedding 就多一个模型、一个索引、一份 393MB 的依赖。可以后面作为可选层加上。
- **不跨用户**。一个库一个 owner，多人场景留给部署层。
- **不自动删数据**。

## 状态

0.1.0，M0–M4 已实现（表结构、落盘、抽取、巩固、FSRS 召回、关联图、澄清、关系状态、agenda、遗忘）。M5 Web UI 未做。

已知缺口：

- 巩固的摘要那一层是抽取式的，没有真正的归纳。多轮之后「最近聊过的」会变成同一批事实的重复点名——所以渲染时按「这条主题是否已经在上面出现过」过滤，宁可剩下一条，也不要一份抄了两遍的档案。
- 话题表是手写的，覆盖不了「今年过得怎么样」这种没有属性键的问法。
- 中文和英文之外没有停用词表。
- 不做向量检索：同义改述（「做插画」vs「画画的」）靠 bigram 命中不了。规模上够用，语义上不够。
- 子集去重只在写入时和升级时各做一次。库里若已存在两条同谓词、一长一短的事实，靠的是 schema 10 的迁移清理；没有在每次渲染时反复重算，因为那是 O(n²) 的字符串比较，而事实数量会涨。
- 一个库一个 owner，多人场景留给部署层。
- 关系状态只有熟悉度、信任、情绪基线三项，没有「近期互动模式」这种更细的东西。
- 他人事实只有一层（「妈妈 health」），没有真正的社交图谱：谁是朋友、谁和谁有关系、某个话题该不该在某个在场者面前提。
- 相对时间解析的是**说出口的**日期，不是**事件**锚点：「过年之前」「发了工资以后」「等结果出来」这类没有解析，英文的 `before the holidays` 同理。loop 的开启、关闭、渲染都已经是双语的，日期解析也是了，剩下的是这类没有日历坐标的说法。
- 情绪词表、话题扩展、抽取提示词都以中文为主；英文能跑通 loop 与渲染，但抽取质量没有在英文对话上验证过。
- 遗忘的粒度是「整条摘要」：一句被删的原话会让覆盖它的整条 reflection 作废，哪怕那条摘要里其余七句都还在。句子级的溯源要么存 span 偏移（重构摘要时就失效），要么重写摘要（要再调一次模型），都还没有。
